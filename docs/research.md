# TestPilot 调研与立项依据

> 调研快照：2026-09-07。本文记录文章来源、公开项目调研和对新仓库的立项判断。链接、仓库状态、许可证页面和项目文档行号都可能随时间变化；再次实施前应按同一证据路径复核。

## 1. 文章来源与复核边界

本次调研的文章材料来自用户指定的飞牛知识库文件（Markdown 转义后的下划线还原为文件名字符）：

`/vol2/1000/personal-knowledge-vault/raw/wemp/精选文章/2026-09-02-Bug分析_用例生成_日志排查_我用一个AI工作台全搞定_附源码___FEATURED_ARTICLES-v6VLyaK9u8L06Ww1k6W7zA.md`

原文链接为 [微信公众号文章](https://mp.weixin.qq.com/s/v6VLyaK9u8L06Ww1k6W7zA)（2026-09-07 调研快照）。文章正文把工作台称为 **Testilot**，配图使用 **TestPilot**；这两个拼写的关系没有在文章中给出正式说明。

文章及其配图可以支持“作者展示了一个面向软件测试和排障的 AI 工作台”这一事实。正文声称开源了 1.0 版本，但没有给出可直接核验的代码仓库、提交号、版本发布链接或许可证。所谓“附源码”的配图展示了设计文档目录和留言获取方式（如关注后留言 666），没有能确认作者身份的仓库地址。因此，截至本快照，**源码身份、许可证、完整实现范围、可复现安装步骤和运行结果均未核实**。公开检索也没有找到能够确认属于该作者的对应仓库；这不等于断言仓库不存在。

文章自述技术栈为 Vue3 + Element Plus、FastAPI + LangChain，以及保存知识库内容的 SQLite；这些尚未通过源码核实。

文章中的案例和效率数字应按作者自述处理。本文不把文章截图、README 宣传语或模型生成的分析当作测试通过、缺陷修复或性能基准。

## 2. 六类入口及其能力边界

文章把以下六类工作放在同一个工作台中。这里的“入口”是文章描述的任务类型，不代表已经存在可调用的统一 API（2026-09-07 调研快照）。

| 文章任务 | 文章展示的用途 | 建设 TestPilot 时必须保留的边界 |
|---|---|---|
| 用例生成 | 根据需求描述、优先级、关联模块及历史用例生成测试用例 | 生成的是待审核草稿；只有实际执行并保留版本、命令和结果后，才能称为回归证据 |
| Bug 分析 | 结合现象、错误日志、截图和项目知识提出分析 | 模型输出是根因假设和验证计划；不能把“看起来合理”写成已确认根因 |
| 日志排查 | 从日志中定位错误、时间线和可能原因 | 需要明确日志来源、采集时间、脱敏处理和完整性；文章没有证明具备持续采集或现场复现能力 |
| SQL 分析 | 根据 SQL、执行场景和期望结果给出分析建议 | SQL 建议不能替代真实数据库执行计划、数据规模和基线对比；需要数据库适配器和权限边界 |
| 报告生成 | 把测试、缺陷或排障信息整理成报告 | 报告是证据的视图，不能增加原始证据没有的结论；必须能回链到文件、提交和运行记录 |
| 回归规划 | 根据缺陷和修复范围列出回归范围 | 回归清单不等于回归已执行；必须分别记录“计划”“执行”“通过”“受阻” |

因此，第一版的核心不是让模型替代各项目的测试框架，而是把任务、原生执行、结果证据和知识关联起来。模型适合生成候选用例、整理时间线、提出可证伪假设；退出码、断言、真实服务、真机和人工审核决定验收状态。

文章声称“效率提升三倍”等数字属于作者自述。文章没有给出样本数、基线、任务定义、失败率、人工修订量或复现实验；TestPilot 不应把它直接作为目标 KPI。第一轮应先记录实际耗时、人工修改次数、重复排障次数和模型用量，再决定是否扩大范围。

## 4. 对新项目的可行性判断

统一建设可行，前提是统一的是协议、编排和证据，而不是抹平各项目的工具差异。项目可以继续使用自己的 pytest、Go test、Shell fixture、浏览器测试、数据库和真机验收；TestPilot 只通过登记过的适配器调用它们。

建议将系统拆成以下五层：

1. **项目注册**：记录稳定项目 ID、仓库根目录、文档入口、技术栈、运行环境、worktree 关系和维护者。
2. **动作适配器**：登记原生测试、检查、日志采集和诊断命令，并声明参数、超时、副作用、网络、密钥、平台、产物和资源锁。
3. **执行与证据**：保存提交或版本、环境摘要、命令、开始结束时间、退出码、测试计数、脱敏输出、附件和校验值。
4. **分析工作流**：检索项目资料和历史证据，生成用例、时间线、根因假设、验证动作和回归建议。
5. **知识生命周期**：审核、归档、检索、关联、失效标记和跨项目经验复用；索引可重建，项目文档仍是事实来源。

模型和执行器的状态至少要区分：`建议`、`待验证假设`、`已执行`、`已验证`、`受阻`。零测试、跳过、环境缺失、超时、取消和 Runner 错误不能被归并为通过。

知识记录建议关联：

`项目 → 模块 → 提交/版本 → 问题 → 根因状态 → 修复 → 回归用例 → 验证证据`

每条记录还应保留来源路径、内容哈希、提交号、审核状态和最后验证时间。文档被修改、删除或换版本后，索引必须增量更新或标记过期，避免旧结论再次被当成当前事实。跨项目复用应只推广经过审核的步骤和模式；地址、凭据、项目配置和未经验证的猜测不能自动传播。

## 5. 开发前准备工作

在实现 Web 界面或接入模型前，建议先完成以下可审查产物（2026-09-07 调研快照）：

1. **项目清单与工作区规则**：确定首批项目、每个项目的权威 checkout、worktree 关系、脏工作区保护、允许读取的文档范围和禁止写入的路径。
2. **动作契约**：冻结动作 ID、参数类型、超时、网络/密钥/副作用声明、资源锁、取消和产物目录；没有登记的命令不应被任意 Shell 透传。
3. **结果契约**：冻结运行状态、退出码语义、测试计数、警告、日志尾部、附件、建议下一步和证据哈希；明确环境失败与业务失败的区别。
4. **知识契约**：定义来源、版本、摘要、标签、审核人、过期规则、删除/重建索引规则和跨项目共享条件。
5. **安全与隐私边界**：定义密钥和个人知识的排除规则、日志脱敏、最小权限、网络分级、外部写入确认以及保留期限。
6. **并发和资源矩阵**：登记数据库、Redis、GPU、浏览器、设备、端口、安装目录和 Git worktree 的共享关系；先默认串行，只有隔离证据成立后才开放并行。
7. **可重复基线**：为每个试点保存一次直接运行原生入口的基线，包括提交、命令、环境、耗时和结果；TestPilot 接入后要与该基线逐项比对。
8. **验收样本**：准备一个能在有缺陷版本失败、修复版本通过的回归样本，以及一个隐藏答案的历史 Bug 盲测，避免把“检索到原答案”误算成诊断能力。

第一批适合选择 Agent Mail、AI Asset Hub 和 homelab-doctor：它们分别覆盖类型化 Runner/契约、Go 与假 HOME 闭环、Shell fixture 与只读诊断。TS Platform 的真实 PostgreSQL、Redis 和多 worktree 约束适合作为第二批，先用其并发矩阵验证编排器。

## 6. luna-worker 的分工与主代理验收

适合按独立任务拆分，但每个 worker 只接收一个可验收、可回滚的边界，不让多个 worker 同时修改同一份契约或同一个适配器。

| 角色 | 建议职责 | 交付物 |
|---|---|---|
| 主代理 | 冻结三份契约、确定安全边界、协调依赖、审查完整 diff 并执行跨项目验收 | 契约、审查记录、端到端证据和最终状态 |
| luna-worker A | 一个项目的原生动作适配器 | 适配器、最小 fixture、结果映射和路径清单 |
| luna-worker B | 文档索引和增量更新 | 来源定位、内容哈希、失效和重建测试 |
| luna-worker C | 结果归档或报告视图 | 结构化结果导入、脱敏附件和可追溯链接 |

主代理验收不能只看 worker 的“测试通过”摘要，应逐项复核命令确实调用项目原生入口、断言覆盖目标行为、失败状态没有被吞掉、日志没有泄露秘密、资源锁与并发规则有效，并在至少三个项目上比较直接运行和统一入口的结果。worker 的任务完成不等于 TestPilot 通过验收；未完成的外部服务、真机或账号验证应明确记为 `受阻`。

## 7. 待定项

以下事项不应在没有新证据时写成结论：飞牛文章“附源码”对应的真实仓库和许可证；候选项目当前版本及其部署依赖；索引和证据存储的具体实现及 AgentMemory 的后续适配；以及真实项目日志和数据库凭据的授权范围。首版 CLI 优先已经确定，Web 属于后续候选。其余事项按 [开发前准备](preparation.md) 和 [架构决策](architecture.md) 处理；本文中的分工建议以 [实施计划](implementation-plan.md) 为准。
